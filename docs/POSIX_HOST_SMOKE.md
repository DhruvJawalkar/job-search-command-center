# macOS and Linux host smoke

`scripts/posix-host-smoke.sh` is a deliberately small, disposable acceptance run for a new local installation on macOS or Linux. It is not a replacement for unit tests or a claim that every Docker Desktop/Engine configuration behaves identically.

From a fresh clone, with Docker running:

```bash
chmod +x setup.sh scripts/posix-host-smoke.sh
./scripts/posix-host-smoke.sh --empty
# Repeat once where practical:
./scripts/posix-host-smoke.sh --demo
```

It verifies Git/Docker/Compose prerequisites, non-interactive `setup.sh`, the empty or synthetic-demo installation mode, service health, 34 migrations, gateway-only isolated loopback ports, local-only data-service egress probes, bind-mount reads/writes, `.env` mode `0600`, stop/start persistence, and gateway recovery after recreating API and portal. The output workspace under `tmp/jscc-posix-smoke-*` contains a text transcript and JSON result. By default the Compose project is stopped with `down --remove-orphans`, never `--volumes`, and the workspace/evidence is retained. `--keep-stack` is for diagnosis; `--remove-workspace` removes only the exact labelled workspace generated by that invocation. Provide `--evidence-dir PATH` before `--remove-workspace` to retain a copy.

The harness intentionally does not make a privacy choice. On a real browser after a fresh empty installation, record this manual checkpoint: the **Privacy & intelligence** modal appears before profile onboarding; select and save one policy, then retain a screenshot or test record stating the selected mode. This is a consent decision, not an automation target.

macOS notes: Docker Desktop must be permitted to share the checked-out clone and the generated `tmp` workspace. Docker Desktop's host UID/GID presentation is a file-sharing implementation detail, so the harness proves bidirectional bind-mount access but does not assert numeric host ownership on macOS. Linux records host UID/GID through `setup.sh`; if the mount test fails, inspect filesystem ACLs and rootless-Docker configuration before retrying. On either OS, do not run this against a live workspace or the normal `job-search-command-center` Compose project.

## macOS CI boundary

`.github/workflows/macos-installer-preflight.yml` runs a short Apple Silicon and Intel preflight on real GitHub-hosted macOS VMs. It checks the Git executable bit, LF/POSIX parsing, required BSD/macOS tools, a fresh local clone whose path contains spaces, and clear Docker-not-running and Compose-v2-missing prerequisite messages. It records the runner architecture and preserves a small JSON evidence artifact.

The hosted macOS preflight does not claim Docker Desktop runtime coverage. GitHub-hosted macOS runners do not reproduce a supported local Docker Desktop installation with host bind mounts and loopback networking. Full macOS runtime evidence therefore still requires an appropriate Mac host; otherwise that limitation must remain explicit in the release evidence.
